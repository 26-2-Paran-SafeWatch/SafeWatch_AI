# 딥러닝 차선 인식 전환 계획

**버전** 0.2 (1~2단계 결과 · 3단계 실행 경로 구현)
**작성** 설만수
**최종 수정** 2026-11-07

이 문서는 LANE 모듈을 OpenCV 규칙 방식에서 딥러닝 모델로 바꾸기로 한 결정과 그 근거, 채택까지의 검증 단계를 기록한다. 현재 동작하는 방식의 상세는 [`pipeline-architecture.md`](pipeline-architecture.md) 3.3에 있다.

---

## 1. 결정 사항

| # | 결정 | 상태 |
|---|---|---|
| D1 | 차선 인식을 **딥러닝 모델로 전환**한다. 단, 2장의 합격 기준을 모두 통과해야 실제로 채택한다 | 결정 (2026-11-06) |
| D2 | 1순위 모델은 **UFLDv2 ResNet18** (MIT 라이선스). CULane 공개 가중치에서 시작하고, 정확도가 부족하면 CLRerNet / CLRNet을 검토한다 | 결정 |
| D3 | **offset을 원본 화면 기준으로 계산**한다. 차량 바닥 높이에서 좌우 차선 x를 읽어 차로 안 위치 비율을 내고, 미터 환산은 그 높이의 차로 폭을 3.5m로 본다. 사다리꼴 보정(`lane.perspective`)이 필요 없어진다 | 결정 |
| D4 | 원칙은 **"선은 딥러닝이 찾고, 믿을지는 규칙과 검증이 정한다"**이다. 모델 출력 뒤에 안전장치(3장)를 두고, 보류 기준은 정답 라벨로 정한다. 통과분 오답 0 원칙은 유지한다 | 결정 |
| D5 | 기존 OpenCV 방식은 지우지 않는다. `lane.method: opencv \| ufld` 설정으로 남겨, 같은 영상으로 비교하고 NPU가 없을 때 대체 경로로 쓴다 | 결정 |
| D6 | 학습 데이터는 필요한 만큼만 단계적으로 추가한다 (4장). **검증은 한국 도로 정답 라벨로만** 한다 | 결정 |
| D7 | 연산은 **NPU**에 맡긴다. YOLOv8n도 함께 옮긴다 | 결정 (기종 미정 — 6장) |

### 전환 이유

1. **가용률이 낮다.** 보정이 정확히 맞는 AI Hub 화면에서도, 판정 임계값을 통과하는 프레임이 17~19%뿐이다(차량 영역 제외 + 기준값 0.47, `pipeline-architecture.md` 3.3 v0.18). 맞게 잡았는데도 버려진 프레임을 분해하면 폭 타당성은 0.85로 양호했다. 신뢰도를 깎은 주범은 점선과 앞차 가림으로 인한 낮은 윈도 적중률(적중률 × 피팅 품질 0.53)이다. 규칙 방식은 보이지 않는 선을 이어서 추정하지 못한다.
2. **카메라마다 보정이 필요하다.** 조감도 변환이 알고리즘의 전제라서, 장착 위치나 각도가 바뀌면 사다리꼴을 다시 맞춰야 한다. 모든 카메라 입력에 보정값을 넣는 것은 현실적으로 어렵다. 장착이 다른 카메라 196장에서는 통과가 0장이었다(보류로 빠짐).
3. **연산 제약이 풀렸다.** NPU를 달기로 하면서, AGENTS.md가 딥러닝 차선 모델을 쓰지 않은 이유(성능 제약)가 사라졌다.

> Pi 실행에서 차선을 못 잡은 직접 원인은 보정 문제가 아니었다. 시험 영상이 AI Hub 화면으로 만든 것이라 보정은 맞아 있었고, 실패 원인은 점선, 가림, 앞차 모서리 오인이었다. 전환의 근거는 "보정이 맞는 최적 조건에서도 가용률이 낮고, 카메라가 바뀌면 그마저 다시 보정해야 한다"는 것이다.

### 예상 이점과 새로 생기는 위험

| 구분 | 내용 |
|---|---|
| 이점 — 가림·점선 | 도로 전체 맥락으로 끊긴 구간도 이어서 예측한다. 가용률을 올릴 가능성이 가장 큰 부분이다 |
| 이점 — 카메라 보정 | 원본 화면에서 바로 선을 찾는다. D3(원본 화면 offset)와 함께 바꿔야만 생기는 이점이다 |
| 이점 — 옆 차로 | 차선 4개를 직접 출력하므로, 지금처럼 폭을 바깥으로 연장해 추정하지 않아도 된다 |
| 이점 — 곡선·언덕·조명 | 노면이 평평하다는 가정과 밝기 고정 규칙에서 벗어난다. 조명 조건은 학습 데이터에 그런 장면이 있을 때만 강해진다 |
| **위험 — 지어내기** | 차선이 없거나 지워진 곳, 합류·분기 구간에 그럴듯한 선을 높은 확신으로 낼 수 있다. 판정 단서가 모두 차선 위치 하나에 달려 있어서, 틀린 차선은 바로 오탐으로 이어진다. 3장 안전장치와 2장 오답 0 기준으로 막는다 |
| 위험 — 개발 비용 | NPU 변환과 양자화, 학습 데이터 형식 변환이 필요하다 |

## 2. 합격 기준

기준선은 현재 방식이다. 검증 247장에서 가용률 17~19%, 통과분 오답 0이고, 보정이 다른 카메라 196장에서는 통과 0이다. 새 방식은 아래를 **모두** 넘어야 채택한다. 수치 목표는 초안이며 팀에서 조정할 수 있다.

| 지표 | 목표 | 의미 |
|---|---|---|
| 검증 247장 통과분 오답 | **0 유지** | 양보하지 않는다 |
| 검증 247장 가용률 | **40% 이상** (지금의 2배 이상) | 가림·점선 문제 해결 |
| 보정이 다른 카메라 196장 | 통과하면서 오답 0 | 카메라마다 보정할 필요가 없다는 직접 증거 |
| Pi5 + NPU 전체 처리 속도 | 15fps 이상 | 실시간 판정 |
| 우리 카메라 영상 약 100장 (직접 라벨링) | 오답 0 | 실차 조건 |

"오답"은 지금과 같이 차로 중심 오차가 차로 폭의 10%를 넘는 경우다(`MAX_ERR`, 잠정값). 다만 **오차는 원본 화면에서 잰다.** 같은 행에서 정답 자차 차로의 좌우 경계와 예측 경계를 비교한다.

### 합격 기준 재검토 안 (팀 결정 대기)

노트북 21번 셀에서 "오답 = 어느 한 행이라도 0.10 초과"를 둘로 나눠 보는 안을 시험했다. 판단 로직(RISK)이 프레임 하나가 아니라 5프레임 이동평균 offset 시계열을 보고, 차선 걸침 임계가 0.25이기 때문이다.

- **큰 오차(차로 폭 0.25 초과) 0건** — 한 프레임으로도 걸침 판정을 뒤집을 수 있는 크기
- **작은 오차(0.10~0.25)는 통과 프레임의 2% 이하**

결과를 보고 잣대를 옮기는 것으로 보이지 않도록 허용 비율 후보(0/1/2/5%)는 미리 정했다. **채택 여부는 팀·지도교수 결정**이며, 채택 전까지 아래 결과는 지금 기준(엄격)으로 읽는다.

## 2-1. 1~2단계 결과 (노트북 `safewatch_lane_calib_v2.ipynb` 15~22번 셀, 2026-11-06~07)

검증 = AI Hub 검증 시퀀스(HOLD), 틀어짐 = 장착이 다른 카메라 196장(MIS, 판정에만 사용). 칸 = 가용률 / 오답.

| 셀 | 내용 | 결과 |
|---|---|---|
| 15 | 공개 가중치 그대로 | CULane이 TuSimple보다 뚜렷이 나음. 틀어짐 카메라에서도 90% 안팎을 잡음(지금 방식 0%) — **카메라 보정 불필요의 직접 증거** |
| 16 | 학습 없는 안전검사(최댓값·잔차·소실점·두 입력 일치) | 오답을 못 거름 → 채택 안 함 |
| 17 | 정답 쌍 점검 | 4번 셀 정답 생성이 칸마다 따로 라벨된 점선을 건너뛰는 버그 발견 → 정답 v2. 틀어짐 오답 15 → 2 |
| 18·19 | AI Hub 보정용 시퀀스(약 800장)로 파인튜닝 | **효과 없음** — 4에폭 이후 과적합, 오답 0 임계가 오히려 사라짐. 정답 v3(겹선 합치기) 도입. 사전학습이 최선 |
| 19 | 측정 범위 | 범위 위끝 0.68에서만 검증 오답 0(91%). **앞차 바닥 높이 중앙값 0.56 — 0.68 안에 드는 앞차는 약 14%** |
| 20 | 걸침 규칙 + 두 모델 일치 | 효과 미미 |
| 21 | 2단계 기준 | 기준을 완화해도 틀어짐에 큰 오차 2~9건 → 원인은 **가까운 선(노란 중앙선·점선)을 건너뛰고 한 칸 바깥 선을 잡는 오류**(폭 약 2배) |
| 22 | 차로 폭 검사(정답 안 씀) | 한 칸 건너뜀 오류 대부분 걸러짐(범위 0.68 틀어짐 큰 오차 6 → 2). 기준 폭은 주행 중 중앙값(시퀀스)이 카메라 전체 중앙값보다 나음. 최선 조합(범위 0.68 + 두 모델 일치 + 폭 ±0.15~0.40)에서 검증 83~92%/0, 틀어짐 0.10 초과 1건(갈림길 한 장면) |

**남은 문제**
1. **먼 쪽 정밀도** — 범위 0.56·0.60은 큰 오차가 아니라 작은 오차 비율(검증 약 5%)에 막힌다. 폭 검사로는 못 거른다 → 대규모 학습 데이터 필요(4장)
2. **한국 도로 특유 장면** — 노란 중앙선·갈림길에서 한 칸 건너뜀. 폭 검사로 대부분 막지만 근본 대책은 학습 데이터
3. **갈림길·합류 구간의 정답 정의** — 차로가 갈라지기 시작하는 곳에서 '자차 차로'가 모호하다. 라벨 규칙을 정하고, 실시간에서는 보류하는 쪽으로 처리해야 한다
4. **측정 거리 범위** — 모델과 무관한 설계 결정. 범위를 넓히려면 1번이 먼저 풀려야 한다

## 3. 구조와 안전장치

```
카메라 프레임
 ├─ YOLOv8n (NPU) ─ 차량 박스 ─ ByteTrack
 └─ UFLDv2-ResNet18 (NPU) ─ 차선 4개(행별 x 좌표 + 차선별 존재 확률)
        └─ 안전장치(CPU) ─ 존재 확률 기준 + 기하 검사 + 프레임 간 일관성 → valid / 보류
                 └─ offset 계산 (원본 화면 기준, D3) → METRICS → RISK (규칙 기반, 변경 없음)
```

모델 출력은 아래를 모두 통과해야 `valid`가 된다. 하나만 걸려도 보류된다는 지금의 원칙(신뢰도를 곱으로 계산)을 그대로 따른다.

1. **존재 확률 기준** — 자차 좌우 차선의 존재 비율 또는 확률이 기준값 이상이어야 한다. 기준값은 지금 0.47을 정한 것처럼 정답 라벨에서 오답이 0이 되는 지점으로 정한다.
2. **기하 검사** — 보정값 없이 원근 화면에서 성립해야 하는 성질을 본다. 좌우 차선이 같은 소실점으로 모이는지, 차로 폭이 화면 아래로 갈수록 일정한 비율로 넓어지는지, 이웃 차로의 폭이 비슷한지를 확인한다.
3. **프레임 간 일관성** — 직전 몇 프레임에 비해 차선 위치가 갑자기 튀면 보류한다.
4. **차량 위 차선 점검(선택)** — 차선 점이 차량 박스 안쪽에 많이 있으면 지어낸 선일 가능성이 높으므로 신뢰도를 낮춘다.

### 3-1. 실제 구현 (v0.2, 2026-11-07, 브랜치 `feature/lane-ufld`)

| 파일 | 내용 |
|---|---|
| `src/lane/ufld.py` | 전처리·행 방향 출력 해석(노트북 15번 셀과 같은 식), 추론 백엔드 추상화(`UFLDBackend`) + ONNX Runtime 구현. NPU 런타임은 같은 모양으로 추가하면 된다 |
| `src/lane/ufld_guard.py` | 안전장치 — 아래 표 |
| `src/lane/ufld_detector.py` | 위 둘을 묶어 `LaneModel(space="image")`을 낸다. 추론 실패는 그 프레임만 보류 |
| `src/lane/__init__.py` | `create_lane_detector(cfg)` — `lane.method: opencv \| ufld` (기본 opencv) |
| `src/metrics/offset.py` | `space="image"`면 차량 바닥 행에서 바로 offset (D3) |
| `scripts/export_ufld_onnx.py` | 원 저장소 가중치 → ONNX. **열 방향 출력을 잘라내** 마지막 층이 약 35% 작아진다(파라미터 206M → 139M, 결과 동일) |

| 안전장치 | 기준 (`lane.ufld.guard`) | 근거 |
|---|---|---|
| 존재 비율 | 측정 구간 안 존재 비율 ≥ 0.68 | 21번 셀 범위 0.68 엄격 기준 |
| 형상 | 구간 위·아래 끝에서 좌 < 우 | — |
| 걸침 | 화면 가운데가 예측 차로 안 (여유 ≥ 0) | 기하 조건. 22번 F-1의 1050 사례 |
| 차로 폭 | 최근 10초 폭 중앙값의 ±25% 밖이면 보류, 기록 15장 전엔 보류 | 22번 셀. 실시간이라 '과거 기록만' 쓴다(노트북은 시퀀스 전체의 나머지 프레임) |
| 프레임 간 일관성 | 기본 끔 | 1초 간격 사진으로는 검증 불가 — 연속 영상 검증 후 결정 |

**계획에서 뺀 것**
- 소실점 등 기하 검사 — 16번 셀에서 효과 없음
- 두 모델 일치 검사 — 22번에서 효과는 있었지만 모델을 두 번 돌려야 해 NPU·연산 예산상 채택 안 함
- 차량 위 차선 점검 — 아직 근거 데이터 없음

**측정값 (개발 맥, 2026-11-07)**
- 전처리 약 1ms(1280×720 입력, `cv2.dnn.blobFromImage`로 17ms에서 줄임), 출력 해석 약 2ms, 안전장치 0.1ms
- **CPU 추론(ONNX Runtime, 무작위 가중치·실제 크기): 4스레드 141ms, 1스레드 433ms.** Pi5 CPU는 이보다 몇 배 느리므로 **CPU만으로는 실시간이 안 된다** — NPU가 사실상 필수이고, 막히면 출력부를 줄여 다시 학습해야 한다(6장)

**아직 확인 못 한 것**
- **실제 가중치로 이 코드와 노트북 결과가 같은지** — 저장소에 가중치가 없어(드라이브 보관) 가짜 출력·무작위 가중치로만 검증했다. 다음 단계에서 코랩으로 대조한다
- 320px 입력에서의 정확도 — 노트북은 원본 해상도로 평가했다

| 기본 | CULane 공개 가중치 (TuSimple 가중치도 1단계에서 비교) | 항상 |
| 한국 도로 보정 | AI Hub `016.도로주행영상` 차선 라벨. **검증 시퀀스는 학습에서 제외** | 1단계에서 기준에 못 미치거나, 한국 특유의 표시를 오인할 때 |
| 조건 다양화 | BDD100K. 진행 방향 차선만 남기고, 연석·횡단보도·정지선을 빼고, 이중선을 합쳐 UFLD 형식으로 변환 | 야간·비·가림 구간이 약할 때 |
| 국내 보강 | 포티투닷 차선 데이터셋 | AI Hub만으로 부족할 때 |
| NPU 양자화 기준 이미지 | AI Hub 학습 시퀀스 수백 장 | 4단계 |
| **최종 검증** | AI Hub 검증 247장 + 보정이 다른 카메라 196장 + 우리 카메라 영상 약 100장 | 학습에 절대 넣지 않음 |

**BDD100K를 쓸 때 주의할 점**
- 같은 차선의 라벨이 연속 프레임 사이에서 흔들리는 경우가 있다.
- 가려지거나 도색이 없는 구간까지 이어서 라벨링되어 있다. 이 때문에 "지어내기" 성향을 같이 배울 수 있다.
- 미국 도로라서 한국의 파란 버스전용차로 선이나 분홍·초록 유도선은 없다.

데이터셋 라이선스는 CULane과 BDD100K 모두 학술용이다. 파란학기 과제로는 문제없지만, 상용화를 생각한다면 다시 검토해야 한다.

## 5. 진행 단계

| 단계 | 내용 | 통과 조건 | 실패하면 | 상태 |
|---|---|---|---|---|
| **1. 그대로 시험** | 공개 가중치를 학습 없이 검증셋에 돌림. `notebook/safewatch_lane_calib_v2.ipynb` 15~22번 셀 | 오답 0이면서 가용률이 19%보다 뚜렷이 높고, 196장에서도 맞게 잡음 | 2단계 | **부분 통과** — 범위 0.68에서 검증 87~91%/0, 틀어짐은 큰 오차 2건 남음 (2-1) |
| 2. 파인튜닝 | AI Hub 라벨로 학습. 약점이 보이면 BDD100K 추가 | 2장 목표 달성 | CLRerNet 검토 | **1차(약 800장) 효과 없음** → Training 데이터(정답 v3 22,745장, 검증 시퀀스·20200916 제외)로 재시도 준비 완료 — `scripts/prepare_ufld_dataset.py`·`scripts/train_ufld.py`, 절차 `docs/ufld-training-guide.md` (2026-11-07). 데스크탑 실행 대기. NPU용 작은 출력부는 그다음 |
| 3. 파이프라인 반영 | `src/lane`에 UFLD 경로와 안전장치 추가, `src/metrics/offset.py`를 원본 화면 기준으로 변경, 테스트·문서 | 기존 테스트 + 새 테스트 통과 | — | **구현 완료(3-1)**, 전체 테스트 126개 통과. 실제 가중치 대조 남음 |
| 4. NPU 변환 | INT8 양자화 후 NPU 실행 파일 생성 | 양자화 뒤에도 오답 0, 가용률 하락 2%p 이내 | 양자화 기준 이미지 조정, 입력 크기 축소, 출력부 축소 후 재학습 | — |
| 5. Pi 실측 | YOLO와 함께 NPU에서 실행 | 전체 15fps 이상 | 차선 모델을 2프레임에 1번 실행 + 사이 프레임 보간 | — |
| 6. 실차 검증 | 우리 카메라 영상 약 100장 | 오답 0 | 우리 데이터로 추가 파인튜닝 | — |

**1단계 평가 방식 (15번 셀)**
- **비교 대상:** P(이전 방식, 0.5)와 V(현재 저장소 방식, 0.47)의 조감도 피팅을 원본 화면으로 되돌려, UFLD와 같은 기준으로 잰다.
- **UFLD 입력 방식 2가지:** 화면 전체를 넣는 `full`과, 학습 데이터 화면 비율로 아래쪽만 잘라 넣는 `bottom`을 비교한다. 둘 다 카메라 보정이 필요 없다.
- **신뢰도:** 자차 좌우 차선 각각 "존재"로 판정된 행의 비율 중 작은 값을 쓴다. 원 저장소 데모는 이 값이 0.5를 넘으면 차선으로 채택한다. 0.3~0.9로 바꿔 가며 가용률과 오답을 본다.
- **후처리 검증:** 셀의 후처리는 원 저장소 `demo.py`의 `pred2coords`(행 방향 차선)와 같은 결과를 내는 것을 확인했다(2026-11-06, 무작위 출력으로 비교).

## 6. 미결 사항과 위험

| 항목 | 내용 | 다음 행동 |
|---|---|---|
| **NPU 기종** | Hailo-8L(AI HAT+, 13 TOPS)인지 Hailo-10H(AI HAT+ 2)인지에 따라 변환 대상이 달라진다 | HW 파트(강섬희) 확인 |
| **모델 크기** | UFLDv2는 출력부가 하나의 큰 완전연결층이다. ResNet18 기준 파라미터가 CULane판 약 206M(fp32 825MB), TuSimple판 약 96M(385MB)이고 대부분이 이 층이다. 칩 안에 가중치를 올리는 NPU에서는 메모리와 속도의 병목이 될 수 있다 | 4단계에서 확인. 크면 행 수·격자 수를 줄여 출력부를 작게 다시 학습(2단계와 함께) |
| Hailo 공식 지원 | Hailo Model Zoo의 Hailo-8L 목록에 차선 검출 모델이 없다. 커뮤니티에서 `ufld_v2_tusimple`을 Hailo-8L용으로 변환한 선례는 있다 | 막히면 출력부 수정, 또는 CPU에서 ONNX 실행 |
| Pi5 실측 속도 | Pi5는 PCIe 1레인이라 공식 수치보다 낮다. YOLOv8n이 공식 182 FPS 대신 약 62 FPS로 나왔다는 보고가 있다 | 5단계 실측 |
| 원본 화면 offset의 정확도 | 원근 화면에서는 같은 행 안에서도 거리 비율이 정확히 보존되지 않는다. 차로 중심 근처의 작은 offset에서는 오차가 작다 | 3단계에서 지금의 조감도 offset과 비교 |
| 우리 카메라 영상 | 6단계 실차 검증에 필요하다 | 장착 확정 후 촬영 |
