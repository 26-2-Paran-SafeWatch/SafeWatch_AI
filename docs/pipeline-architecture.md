# 파이프라인 구조 설계서

**버전** 0.2 (미결 사항 보강)
**작성** 설만수
**최종 수정** 2026-09-10

이 문서는 SafeWatch AI 모듈의 내부 구조와 모듈 간 데이터 흐름을 정의한다. 구현 진행에 따라 갱신한다.

---

## 1. 설계 원칙

### 1.1 모듈 경계의 명확성

각 모듈은 정의된 입출력만으로 통신하며, 다른 모듈의 내부 구현에 의존하지 않는다. 차선 인식 방식이 OpenCV에서 딥러닝으로 바뀌더라도 상위 로직은 영향받지 않아야 한다.

### 1.2 플랫폼 차이의 국소화

PC 개발 환경과 Pi5 타깃 환경의 차이는 `input`, `detection` 두 모듈에서만 흡수한다. 상위 로직은 어느 플랫폼에서 실행 중인지 알 필요가 없다.

### 1.3 성능 예산의 명시

프레임당 전체 처리 시간 목표는 **100ms 이하(10fps)** 다. 각 단계에 예산을 배분하고, 실측을 통해 병목을 관리한다.

### 1.4 실패 격리

단일 프레임 처리 실패가 전체 파이프라인을 중단시키지 않는다. 차량 환경에서 장시간 무중단 구동이 요구되기 때문이다.

## 2. 전체 구조

```
┌─────────────────────────────────────────────────────────┐
│                      INPUT LAYER                         │
│  picamera2 (Pi5) / cv2.VideoCapture (PC)                │
│  → Frame(image, timestamp, frame_id)                    │
└────────────────────────┬────────────────────────────────┘
                         │
        ┌────────────────┴────────────────┐
        ▼                                 ▼
┌───────────────────┐            ┌───────────────────┐
│    DETECTION      │            │       LANE        │
│  YOLOv8n          │            │  OpenCV           │
│  → VehicleBox[]   │            │  → LaneModel      │
└─────────┬─────────┘            └─────────┬─────────┘
          │                                │
          ▼                                │
┌───────────────────┐                      │
│    TRACKING       │                      │
│  ByteTrack        │                      │
│  → TrackedVehicle[]                      │
└─────────┬─────────┘                      │
          │                                │
          └────────────┬───────────────────┘
                       ▼
          ┌───────────────────────┐      ┌──────────────┐
          │       METRICS         │◄─────│  IMU INPUT   │
          │  lane offset 산출     │      │  (ESP32)     │
          │  시계열 버퍼 관리     │      └──────────────┘
          │  → VehicleTimeSeries  │
          └───────────┬───────────┘
                      ▼
          ┌───────────────────────┐
          │         RISK          │
          │  신뢰도 게이팅        │
          │  지표별 점수 산출     │
          │  결합 판정            │
          │  → RiskAssessment     │
          └───────────┬───────────┘
                      ▼
          ┌───────────────────────┐      ┌──────────────┐
          │        EVENT          │─────►│   PRIVACY    │
          │  클립 추출            │      │  번호판·얼굴 │
          │  JSON 생성            │◄─────│  블러 처리   │
          │  전송 큐 적재         │      └──────────────┘
          └───────────┬───────────┘
                      ▼
              서버 전송 / 로컬 저장
```

## 3. 모듈별 명세

### 3.1 INPUT — 영상 입력

**책임** 카메라 또는 영상 파일에서 프레임을 획득하고 타임스탬프를 부여한다.

**플랫폼 분기**

| 환경 | 구현 |
|---|---|
| Pi5 | `picamera2` — DMA 버퍼에서 zero-copy 수신 |
| PC | `cv2.VideoCapture` — 파일 또는 웹캠 |

**출력**

```python
@dataclass
class Frame:
    image: np.ndarray          # BGR, (H, W, 3)
    timestamp: float           # Unix epoch, 초 단위 소수점
    frame_id: int              # 순차 증가
```

**설계 노트**
- 타임스탬프는 IMU 데이터와의 동기화 기준이므로 프레임 획득 즉시 부여한다
- 프레임 드롭이 발생해도 `frame_id`는 건너뛰지 않고 연속 증가시켜 누락을 추적할 수 있게 한다

**성능 예산** 5ms

---

### 3.2 DETECTION — 차량 검출

**책임** 프레임에서 전방 차량을 검출한다.

**입력** `Frame`
**출력**

```python
@dataclass
class VehicleBox:
    x1: float; y1: float; x2: float; y2: float   # 픽셀 좌표
    confidence: float
    class_id: int              # car, truck, bus 등
```

**처리**
1. ROI 크롭 — 하늘·갓길 제외, 전방 차선 영역만 처리
2. 리사이즈 — config의 입력 해상도로 (Pi5: 320)
3. YOLOv8n 추론
4. confidence·NMS 필터링
5. 좌표를 원본 프레임 기준으로 역변환

**검출 주기 분리**

매 프레임 추론하지 않고 `detection.interval` 프레임마다 1회 실행한다. 중간 프레임은 TRACKING이 위치를 보간한다. 위험 판단이 초 단위로 이루어지므로 판단 정확도에 영향이 없으면서 처리량을 크게 개선한다.

**플랫폼 분기**

| 환경 | 추론 엔진 |
|---|---|
| Pi5 | ONNX Runtime 또는 NCNN |
| PC | PyTorch |

**성능 예산** 50ms (검출 수행 프레임 기준)

---

### 3.3 LANE — 차선 인식

**책임** 좌우 차선의 위치와 곡률을 산출하고, 결과의 신뢰도를 함께 제공한다.

**입력** `Frame`
**출력**

```python
@dataclass
class LaneModel:
    left_fit: Optional[np.poly1d]     # 2차 다항식 계수
    right_fit: Optional[np.poly1d]
    lane_width_px: Optional[float]
    curvature_radius: Optional[float] # 미터
    confidence: float                 # 0.0 ~ 1.0
    valid: bool
```

**처리**
1. ROI 설정
2. perspective transform — bird's eye view 변환
3. 색상·엣지 기반 차선 후보 추출 (HLS 색공간 + Canny)
4. sliding window로 차선 픽셀 탐색
5. 2차 다항식 피팅
6. 신뢰도 산출 — 피팅 잔차, 좌우 차선 평행도, 검출 픽셀 수

**신뢰도가 중요한 이유**

차선 인식은 이 프로젝트에서 가장 불안정한 구간이다. 차선이 흐린 도로, 앞차에 가려진 차선, 야간·우천 환경에서 성능이 급격히 저하된다. **신뢰도가 낮을 때 판단을 보류하는 것이 잘못된 offset으로 오탐을 만드는 것보다 낫다.**

**폴백 경로**

`valid == False`인 구간에서는 lane offset 기반 지표를 사용하지 않고, IMU 기반 지표만으로 판단한다. 차선 인식이 최종적으로 불안정할 경우를 대비한 설계다.

**성능 예산** 25ms

---

### 3.4 TRACKING — 차량 추적

**책임** 프레임 간 동일 차량에 일관된 ID를 부여한다.

**입력** `VehicleBox[]`
**출력**

```python
@dataclass
class TrackedVehicle:
    track_id: int
    box: VehicleBox
    tracked_frames: int        # 연속 추적 프레임 수
    is_interpolated: bool      # 검출 없이 추적으로 보간된 프레임인지
```

**처리**
- ByteTrack으로 프레임 간 매칭
- 검출이 없는 프레임에서는 이전 궤적으로 위치 보간
- ID switching 발생 시 해당 track의 시계열 데이터를 무효 처리

**관측 충분성 조건**

`tracked_frames`가 config의 최소값(기본 30프레임) 미만인 차량은 거동 분석 대상에서 제외한다. 잠깐 스쳐간 차량의 거동은 신뢰할 수 없다.

**성능 예산** 10ms

---

### 3.5 METRICS — 지표 산출

**책임** 차량과 차선의 관계를 수치화하고 시계열로 축적한다.

**입력** `TrackedVehicle[]`, `LaneModel`, `IMUData`
**출력**

```python
@dataclass
class VehicleTimeSeries:
    track_id: int
    offsets: deque[OffsetSample]      # 최근 N초
    direction_changes: int
    max_offset_ratio: float
    departure_duration_sec: float

@dataclass
class OffsetSample:
    timestamp: float
    offset_m: float                   # 차선 중심 대비 편차, 부호 있음
    offset_ratio: float               # 차로 폭 대비 비율
    lane_confidence: float
```

**lane offset 산출 방법**
1. 차량 bounding box 하단 중심점을 차량 위치로 정의
2. 해당 y좌표에서의 차선 중심 좌표 계산
3. 두 점의 픽셀 거리 산출
4. 캘리브레이션으로 실거리(m) 변환 — 차로 폭 3.5m 기준
5. 차로 폭 대비 비율로 정규화

**보정 처리**

| 보정 | 목적 |
|---|---|
| 자차 거동 보상 | IMU yaw/roll로 자차 흔들림 제거. 자차가 흔들리면 앞차가 흔들려 보이는 착시 방지 |
| 곡선 도로 보정 | 차선 곡률 기반 기대 궤적을 기준선으로 사용. 정상 곡선 주행의 오판 방지 |
| 시계열 평활화 | 이동평균 또는 칼만 필터로 단일 프레임 이상치 제거 |

**시계열 버퍼**

차량별로 최근 `risk.observation_window_sec`(기본 10초) 구간의 offset 이력을 유지한다. 차량이 화면에서 사라지면 버퍼를 해제한다.

**IMU 동기화**

IMU 데이터는 영상 프레임과 다른 주기로 도착한다. 타임스탬프 기준으로 가장 가까운 샘플을 매칭하며, 허용 오차를 초과하면 해당 지표를 무효 처리한다.

**성능 예산** 5ms

---

### 3.6 RISK — 위험 판단

**책임** 시계열 지표로부터 위험 점수를 산출하고 이벤트 생성 여부를 결정한다.

**입력** `VehicleTimeSeries`, `LaneModel.confidence`, `Frame` 품질 정보
**출력**

```python
@dataclass
class RiskAssessment:
    track_id: int
    score: int                        # 0 ~ 100
    level: str                        # low / medium / high
    types: list[str]                  # 감지된 위험 유형
    indicators: dict                  # 지표별 측정값
    should_emit_event: bool
```

**처리 순서**

```
1. 입력 신뢰도 게이팅
   ├ 검출 confidence 미달 → 판단 보류
   ├ 차선 인식 신뢰도 미달 → offset 기반 지표 제외
   ├ 프레임 품질 미달 (블러·밝기 급변) → 판단 보류
   └ 관측 충분성 미달 → 판단 보류
              ↓
2. 지표별 점수 산출
   ├ 차선 걸침 — offset 비율 및 지속 시간
   ├ 사행 — 방향 전환 횟수 및 진폭
   ├ 급가감속 — IMU 종방향 가속도
   └ 급진로변경 — 방위각 변화량
              ↓
3. 결합 판정
   ├ 충족 지표 수 < min_indicators → 이벤트 미생성
   └ 가중 합산으로 통합 점수 산출
              ↓
4. 이벤트 판정
   ├ 히스테리시스 — 시작·종료 임계값 분리
   └ 쿨다운 — 동일 차량 중복 이벤트 억제
```

**임계값의 출처**

모든 임계값은 `docs/risk-criteria.md`에 근거와 함께 정의되어 있으며, config에서 값을 읽는다. **코드에 임계값을 직접 쓰지 않는다.**

**복수 지표 결합의 근거**

NHTSA 연구에서 단일 단서보다 2개 이상의 단서가 동시 관측될 때 판별 신뢰도가 크게 상승함이 확인되었다. 이를 근거로 `min_indicators`를 2로 설정한다.

**성능 예산** 3ms

### 3.7 EVENT — 이벤트 생성

**책임** 위험 이벤트를 클립과 메타데이터로 구성하고 전송을 관리한다.

**입력** `RiskAssessment`, 프레임 링 버퍼
**출력** 이벤트 JSON + 클립 파일

**처리**
1. 링 버퍼에서 전후 구간 프레임 추출 (전 10초 + 후 5초)
2. PRIVACY 모듈로 비식별화 처리
3. 클립 인코딩 및 저장
4. JSON 메타데이터 생성 — 스키마는 `docs/event-schema.md` 준수
5. 전송 큐 적재

**프레임 링 버퍼**

이벤트 발생 시점 **이전** 영상이 증거로서 더 중요하다. 감지되기까지의 거동이 위험 판단의 근거이기 때문이다. 따라서 항상 최근 N초의 프레임을 메모리에 유지한다.

메모리 사용량에 유의한다. 320×320 15fps 10초 = 약 45MB(무압축 기준). Pi5 메모리 여유를 고려해 압축 저장 또는 버퍼 길이 조정이 필요할 수 있다.

**Store-and-Forward**

통신 단절 시에도 이벤트가 유실되지 않도록 로컬 큐에 우선 저장한다.

```
이벤트 발생 → 로컬 저장 (무조건)
              ↓
         통신 가능?
         ├ Yes → 서버 전송 → 성공 시 로컬 삭제
         └ No  → 큐 유지 → 통신 복구 시 재전송
```

재전송으로 인한 중복은 서버가 `event_id`로 판별한다. 이는 앱·서버 파트와 합의된 사항이다.

**성능 예산** 이벤트 발생 시에만 소요. 비동기 처리하여 파이프라인을 차단하지 않는다.

---

### 3.8 PRIVACY — 비식별화

**책임** 외부로 나가는 영상에서 개인식별 정보를 제거한다.

**처리**
- 번호판 검출 후 가우시안 블러 적용
- 보행자 얼굴 검출 후 블러 적용

**설계 노트**

번호판 검출은 YOLO 모델에 클래스를 추가하는 방식으로 구현한다. 별도 모델을 추가하지 않는다.

이벤트 발생 시점에만 수행하므로 상시 성능 부담은 없다. 다만 이벤트가 연속 발생하는 상황에서 병목이 될 수 있어, 비동기 처리 및 큐잉이 필요하다.

**미결 사항** — 비식별화를 Edge에서 수행할지 서버에서 수행할지는 Pi5 성능 여유를 확인한 뒤 확정한다. 현재는 Edge 수행을 기본으로 설계하되, 이벤트 JSON에 `blurred` 플래그를 두어 양쪽 모두 대응 가능하게 한다.

## 4. 성능 예산 요약

| 단계 | 예산 | 비고 |
|---|---|---|
| INPUT | 5ms | |
| DETECTION | 50ms | 검출 수행 프레임만 |
| LANE | 25ms | |
| TRACKING | 10ms | |
| METRICS | 5ms | |
| RISK | 3ms | |
| **합계** | **98ms** | 약 10fps |

검출 주기를 3으로 설정하면 검출 미수행 프레임은 약 48ms로 처리되어, 평균 처리 시간은 이보다 낮아진다.

**실측으로 검증해야 하는 값이며, 위 배분은 초기 목표치다.**

## 5. 미결 사항

| 항목 | 내용 | 결정 시점 |
|---|---|---|
| 추론 엔진 | ONNX vs NCNN, 양자화 적용 여부 | S6 (11~12주차) 실측 후 |
| 비식별화 위치 | Edge vs 서버 | Pi5 성능 여유 확인 후 |
| 차선 인식 방식 | OpenCV 유지 vs 딥러닝 전환 | S3 (5~6주차) 종료 시점 |
| 링 버퍼 저장 방식 | 무압축 vs 실시간 압축 | 메모리 실측 후 |
| AI 가속기 도입 | Hailo AI Kit 등 | S6 초반 성능 판단 후 |
| **IMU 지표의 track_id 귀속 규칙** | 자차 급가감속·방위각변화가 자차 것임에도 특정 전방 차량(target_vehicle)에 귀속되는 판정 로직 부재. "도로 정체로 인한 감속"과 "전방 차량 급끼어들기로 인한 감속"을 구분 못 하면 판단 근거 검증 요구사항을 충족 못 함 | S4 (7~8주차) 임계값 확정 전 필수 |
| **GPS/위치 데이터 입력 경로** | `event-schema.md`의 `location` 필드가 필수인데 구조도(2장)에 GPS 입력 모듈이 없음. ESP32 경유 여부, Pi5 직결 여부, IMU와의 타임스탬프 동기화 방식 미정 — HW팀(강섬희) 조율 필요 | S1~S2 |
| **EVENT 비동기 처리의 동시성 모델** | "비동기 처리로 파이프라인 비차단"이라는 요구사항만 있고 스레드 vs 멀티프로세스, 프레임 링 버퍼의 스레드 안전성 설계가 없음. Python GIL 특성상 CPU-bound 블러·인코딩은 스레드로는 실효 이득이 제한적일 수 있음 | S1~S2 구현 착수 시 |
| **얼굴 블러 검출 방식** | 번호판은 "YOLO 클래스 추가"로 방법이 정해졌으나 얼굴 검출 방법은 미정. "딥러닝 모델 추가 금지" 원칙(AGENTS.md)과 충돌하지 않는 방식(YOLO 클래스 확장 또는 Haar cascade 등 non-DL) 결정 필요 | S4 (PRIVACY 모듈 구현 시) |
| **로컬 저장공간 관리 정책** | Store-and-Forward는 통신 단절만 가정. SD카드 용량 초과 시 정책(오래된 큐 삭제/신규 이벤트 드롭/사용자 알림) 부재. 4시간 이상 연속 구동 KPI 고려 시 실제로 발생 가능한 시나리오 | S7 안정화 이전 |
| **카메라 캘리브레이션 절차** | lane offset의 미터 환산이 캘리브레이션(차로 폭 3.5m 기준)에 의존하나, 수행 시점·방법(1회 수동/자동, 스크립트 유무)이 문서화되지 않음 | S3 (5~6주차) lane offset 구현 전 |
