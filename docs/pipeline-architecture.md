# 파이프라인 구조 설계서

**버전** 0.21 (먼 영역 한 번 더 검출)
**작성** 설만수
**최종 수정** 2026-11-12

이 문서는 SafeWatch AI 모듈의 내부 구조와 모듈 간 데이터 흐름을 정의한다. 구현 진행에 따라 갱신한다.

> **스코프 변경 (v0.5)** — 감지 대상이 "위험운전 전반"에서 **음주운전 의심 차량**으로 축소되었다. 판단 기준은 NHTSA 차로 유지 단서(사행·차선 걸침·스웨빙·표류) 중심이며, IMU는 판정 지표가 아니라 **자차 거동 보정용**으로만 쓴다. 단서 범위와 출력 표현은 **2026-09-26 지도교수 확인으로 확정** — `docs/risk-criteria.md` 1.4 참고.

> 카메라·엣지·클라우드·앱을 아우르는 전체 시스템 컨텍스트는 [`docs/system-architecture.md`](system-architecture.md) 참고. 이 문서(2장 이하)는 그중 엣지(Pi5) 위 AI 모듈 내부만 다룬다.

---

## 1. 설계 원칙

### 1.1 모듈 경계의 명확성

각 모듈은 정의된 입출력만으로 통신하며, 다른 모듈의 내부 구현에 의존하지 않는다. 차선 인식 방식이 OpenCV에서 딥러닝으로 바뀌더라도 상위 로직은 영향받지 않아야 한다.

### 1.2 플랫폼 차이의 국소화

PC 개발 환경과 Pi5 타깃 환경의 차이는 `input`, `detection` 두 모듈에서만 흡수한다. 상위 로직은 어느 플랫폼에서 실행 중인지 알 필요가 없다.

### 1.3 성능 예산의 명시

프레임당 전체 처리 시간 목표는 **100ms 이하(10fps)** 다. 각 단계에 예산을 배분하고, 실측을 통해 병목을 관리한다.

### 1.4 실패 격리

단일 프레임 처리 실패가 전체 파이프라인을 중단시키지 않는다. 차량 환경에서 장시간 무중단 구동이 요구되기 때문이다.

## 3. 모듈별 명세

### 3.1 INPUT — 영상 입력

**책임** 카메라 또는 영상 파일에서 프레임을 획득하고 타임스탬프를 부여한다.

**플랫폼 분기**

| 환경 | 구현 |
|---|---|
| Pi5 | `picamera2` — DMA 버퍼에서 zero-copy 수신 |
| PC | `cv2.VideoCapture` — 파일 또는 웹캠 |

**출력**

```python
@dataclass
class Frame:
    image: np.ndarray          # BGR, (H, W, 3)
    timestamp: float           # Unix epoch, 초 단위 소수점
    frame_id: int              # 순차 증가
```

**설계 노트**
- 타임스탬프는 IMU 데이터와의 동기화 기준이므로 프레임 획득 즉시 부여한다
- 프레임 드롭이 발생해도 `frame_id`는 건너뛰지 않고 연속 증가시켜 누락을 추적할 수 있게 한다
- HW 파트 전체 아키텍처는 카메라가 **lores(640×384, 추론용) / main(1280×720, 저장용) dual-stream**을 동시 출력하는 것을 전제로 한다 (`docs/system-architecture.md` 참고). 이 모듈이 lores 스트림만 받는지, main 스트림(링 버퍼용)도 함께 다루는지는 아직 확인되지 않았다.

**성능 예산** 5ms

---

### 3.2 DETECTION — 차량 검출

**책임** 프레임에서 전방 차량을 검출한다.

**입력** `Frame`
**출력**

```python
@dataclass
class VehicleBox:
    x1: float; y1: float; x2: float; y2: float   # 픽셀 좌표
    confidence: float
    class_id: int              # 가중치의 클래스 id — COCO면 car=2 등, 파인튜닝이면 vehicle=0
```

**처리**
1. ROI 크롭 — 프레임 위쪽 `detection.roi_top_ratio`만큼 잘라낸다. **v0.17부터 0(크롭 없음)** — 아래 "하늘 크롭을 없앤 이유"
2. 리사이즈 — config의 입력 해상도로 (Pi5: 320)
3. YOLOv8n 추론
4. confidence·NMS 필터링
5. 좌표를 원본 프레임 기준으로 역변환
6. (v0.21) 먼 영역 한 번 더 — 아래 "먼 영역 한 번 더 검출"

**검출 주기 분리**

매 프레임 추론하지 않고 `detection.interval` 프레임마다 1회 실행한다. 중간 프레임은 TRACKING이 위치를 보간한다. 위험 판단이 초 단위로 이루어지므로 판단 정확도에 영향이 없으면서 처리량을 크게 개선한다.

**플랫폼 분기**

| 환경 | 추론 엔진 |
|---|---|
| Pi5 | ONNX Runtime 또는 NCNN |
| PC | PyTorch |

**성능 예산** 50ms (검출 수행 프레임 기준)

**하늘 크롭을 없앤 이유 (v0.17)** — 원래는 하늘 영역의 오검출을 줄이려고 프레임 위 45%를 잘라내고 추론했다. 파인튜닝 모델(`vehicle_v1`)의 놓친 근거리 차량을 분석해 보니(`notebook/safewatch_vehicle_finetune.ipynb` 10번 셀, AI Hub 검증 494장, 판정 영역·화면 높이 ≥ 8%), **놓친 204대 중 148대(73%)가 크롭선에 몸통이 잘린 차량**이었다. AI Hub 카메라에서 수평선이 화면 높이 0.45~0.5 근처라, 가까운 차량은 거의 항상 이 선 위로 올라온다.

| 하늘 크롭 (ONNX 320) | 근거리 Recall — 트랙 생성(conf ≥ 0.5) | 추적 유지(≥ 0.1) | 판정 영역 오탐 |
|---|---|---|---|
| 0.45 | 0.724 | 0.776 | 99 |
| 0.35 | 0.839 | 0.908 | 71 |
| **0** | **0.881** | **0.934** | **56** |

크롭을 없애면 오탐도 줄었다 — 잘린 차에 반쪽 박스가 나와 정답과 안 맞던 것이다. 그리고 ONNX·NCNN은 입력이 320×320 고정이라 **위를 잘라도 그만큼 여백으로 채워질 뿐 연산이 줄지 않았다** — 크롭은 정확도만 깎고 있었다. 하늘의 간판·건물 검출은 판정 대상(바닥이 차선 조감도 범위 안인 차량)에 들어가지 않는다.

> **후속 — 직사각형 입력** — 크롭이 없으면 16:9 프레임이 정사각 320 입력의 320×180만 채운다. 직사각형 입력으로 export하면 Pi5 검출 연산을 줄일 여지가 있으나, 카메라 출력 해상도가 확정돼야 크기를 정할 수 있다 (5장 "dual-stream 입력 범위"와 같은 HW 확인 건).

**먼 영역 한 번 더 검출 (v0.21, `detection.far_region`)** — 320 입력에서는 먼 차가 몇 픽셀뿐이라 놓친다. 화면 가로 0.25~0.75 · 세로 0.30~0.65(먼 차 바닥이 있는 곳)만 잘라 같은 모델에 한 번 더 넣고, 잘린 경계에 닿은 박스(몸통이 잘린 차)는 버린 뒤, 전체 화면 검출과 IoU 0.5 미만으로만 겹치는 것을 더한다. 겹치면 전체 화면 박스를 남기되, 먼 영역 박스만 새 트랙 기준(`tracking.track_high_thresh`) 이상이면 그것으로 바꾼다. 근거 — `notebook/safewatch_vehicle_finetune.ipynb` 8·9·10번 셀, AI Hub 검증 494장(1920×1080 원본), 판정 영역 정답 2174대:

| 먼 차 (바닥이 화면 0.58 위, 1587대) | 320 | **320 + 먼 영역** | 640 |
|---|---|---|---|
| 새 트랙 Recall (conf ≥ 0.5) | 0.49 | **0.70** | 0.72 |
| 트랙 잇기 Recall (conf ≥ 0.1) | 0.71 | **0.83** | 0.86 |
| 판정 영역 오탐 (conf ≥ 0.5) | 59 | 329 | 188 |
| 검출 연산 | 1배 | 약 2배 | 약 4배 |

0.58 아래(가까운 차) Recall은 셋 다 0.90~0.91로 같다. 늘어난 오탐 267개 중 중복 박스는 55개이고 212개는 아무것과도 안 겹쳤는데, 확신 높은 48개를 그림으로 보니 거의 전부 **라벨이 안 붙은 실제 먼 차**였다(AI Hub 라벨이 작은 먼 차를 빠뜨림) — 오탐 수는 과대평가다. 합치는 기준을 IoU 0.3·포개짐으로 엄격하게 하면 Recall만 떨어졌다(0.70 → 0.69·0.67). 원본 프레임이 모델 입력보다 충분히 커야 효과가 있어 `pi5.yaml`(320×320 수신)은 끄고 `pi5_ufld.yaml`(1280×720)은 켠다. 맥 CPU ONNX 1280×720 기준 검출 12ms → 32ms (참고용, Pi5 수치 아님).

**파인튜닝 라벨 클래스 매핑 (2026-09-27, AI Hub 도로주행영상 라벨 분석)** — `VEHICLE_CLASS_IDS = {2, 3, 5, 7}`(car/motorcycle/bus/truck, `src/detection/detector.py`)가 이미 차종 구분 없이 "차량"으로 단일 취급하고, `class_id`는 TRACKING(ByteTrack) 내부 처리 외에는 RISK·METRICS·EVENT 어디에서도 참조되지 않는다. 이 시스템에 차종 분류는 애초에 불필요하다는 뜻이므로, AI Hub 라벨의 `Vehicle_Car`/`Vehicle_Bus`/`Vehicle_Motorcycle`/`Vehicle_Unknown`은 파인튜닝 시 **전부 단일 `vehicle` 클래스로 병합**한다. `Vehicle_Unknown`(bb 기준 15,273건, 전체 차량 라벨의 약 22%)을 제외할 근거를 찾기 위해 bbox 크기를 `Vehicle_Car`와 비교했으나 중앙값이 거의 동일해(70px vs 68px, 원거리 소형 객체라서 분류 불가였다는 가설과 불일치) 크기 기반 제외 근거도 없었다 — 그래서 배제하지 않고 포함한다. `pg`(폴리곤) 카테고리의 차량 라벨은 bbox가 아니므로 파인튜닝에 쓰려면 외접 사각형으로 변환하는 과정이 별도로 필요하다.

**차량 클래스는 id가 아니라 이름으로 고른다 (v0.15)** — 위 병합 결과, 파인튜닝 가중치의 클래스는 `vehicle`(id 0) 하나뿐이다. 그런데 차량 필터가 COCO id `{2, 3, 5, 7}`로 하드코딩돼 있어, 가중치만 바꾸면 id 0(COCO에선 person)이 전부 버려져 **에러 없이 차량이 하나도 안 잡히는** 상태였다. 이제 `detection.vehicle_class_names`(`car`·`motorcycle`·`bus`·`truck`·`vehicle`)를 가중치 메타데이터의 클래스 이름과 대조한다 — .pt·ONNX·NCNN 모두 이름이 실려 오므로 사전학습/파인튜닝 가중치를 바꿔도 config를 고칠 필요가 없고, 하나도 안 맞으면 시작 시점에 에러로 멈춘다.

### 3.3 LANE — 차선 인식

> **딥러닝 전환 결정 (v0.19, 2026-11-06)** — 아래는 현재 구현된 OpenCV 방식이다. UFLDv2로의 전환 결정과 합격 기준은 [`lane-detection-dl-plan.md`](lane-detection-dl-plan.md). 합격 전까지는 이 방식이 기본 경로다.
>
> **v0.20 (2026-11-07) — UFLD 실행 경로 추가.** `lane.method: ufld`로 바꾸면 `src/lane/ufld_detector.py`가 쓰인다(기본은 여전히 `opencv`). 출력은 같은 `LaneModel`이되 `space="image"`(원본 화면 점)이고, 안전장치(존재 비율·형상·걸침·차로 폭·선택적 일관성, `src/lane/ufld_guard.py`)를 통과해야 `valid`다. 구조·근거·남은 일은 `lane-detection-dl-plan.md` 3장·5장.

**책임** 좌우 차선의 위치와 곡률을 산출하고, 결과의 신뢰도를 함께 제공한다.

**입력** `Frame`
**출력**

```python
@dataclass
class LaneModel:
    left_fit: Optional[np.poly1d]     # 2차 다항식 계수
    right_fit: Optional[np.poly1d]
    lane_width_px: Optional[float]
    curvature_radius: Optional[float] # 미터
    confidence: float                 # 0.0 ~ 1.0
    valid: bool
    fit_residual_ratio: Optional[float]  # 공유 형상 피팅의 RMS 잔차 / 차로 폭 (튜닝·디버깅용)
```

**처리 (v0.15 — `notebook/safewatch_lane_calib.ipynb`에서 AI Hub 정답 라벨로 검증한 방식)**
1. perspective transform — 사다리꼴 ROI를 bird's eye view로 변환. 사다리꼴은 출력 폭의 양옆 `margin_ratio`(0.18)만큼 안쪽으로 매핑해, 자차 차로 밖(옆 차로·갓길)도 조감도에 남긴다
2. 차선 후보 추출 — 조감도로 **먼저 변환한 뒤** 노면 안에서만: 밝기(HLS L) 수평 top-hat + Otsu 임계 → 무채색(HLS S ≤ `white_s_max`)만 흰 차선으로 인정, 황색은 HLS 범위로 별도 → 세로로 긴 연결 성분만 남김(노면 화살표·문자 제거)
3. 시작 위치 — 하단 절반 열 히스토그램의 피크 후보 중, 화면 중앙을 사이에 두고 폭이 허용 범위(`width_range`) 안인 **가장 안쪽 쌍**
4. 평행 제약 sliding window — 좌우 윈도를 **같은 만큼만** 이동, 윈도 안 위치는 평균이 아니라 **가장 촘촘한 세로 열**(±3px 평균)
5. 공유 형상 피팅 — 두 선을 같은 모양(`a·y² + b·y`)에 위치(`c_left`, `c_right`)만 다른 2차식으로 함께 최소제곱 피팅, 잔차가 큰 점을 한 번 제거한 뒤 다시 피팅
6. 신뢰도 산출 — 아래

**신뢰도 산출 상세**

세 항목의 **곱**이다. 하나라도 0에 가까우면 전체가 0에 가까워져 판정이 보류된다. 값은 `configs/default.yaml`의 `lane.confidence`에 있다.

| 항목 | 산출 | 잡아내는 실패 유형 |
|---|---|---|
| 윈도 적중률 | 피팅에 남은 윈도 점 수 / (2 × 윈도 수 − 차량에 가려진 윈도 수, 하한 윈도 수) — v0.18 | 차선이 안 보이는 구간 (가려짐·먼 거리·흐린 도색) |
| 피팅 잔차 | 공유 형상 피팅의 RMS 잔차가 기대 차로 폭의 `max_rms_ratio`(5%)에 이르면 0 | 좌우 선 모양이 서로 다름 — 한쪽만 난간·잡음을 잡은 경우 |
| 폭 타당성 | 피팅된 차로 폭이 기대 폭(보정값에서 결정)에서 `width_tolerance`(40%) 벗어나면 0 | 한 차로 바깥 선을 잡은 경우, **보정이 틀어진 경우**(장착 변경·충격) |

**이 방식으로 바꾼 이유 (v0.15)** — AI Hub `016.도로주행영상` `60_전방`의 차선 정답 라벨로 보정용과 겹치지 않는 시퀀스 247장을 검증했다(`notebook/safewatch_lane_calib.ipynb` 8번 셀, 처리 폭 320px 포함).

| 방식 | `min_confidence` 0.5 통과 | 그중 오답(중심 오차 > 차로 폭 10%) |
|---|---|---|
| 이전 방식 (좌우 절반 최강 피크 + 독립 피팅 + 가중 합산 신뢰도) | 원본 52장 / 320px 49장 | **8장 / 4장** — 난간·터널 벽·가드레일을 차선으로 잡고도 신뢰도 0.55~0.87 |
| 현재 방식 | 원본 36장 / 320px 35장 | **0장 / 0장** |

보정이 다른 카메라(장착이 다른 차량 시퀀스 196장)에서는 두 방식 모두 0.5 통과가 0장이었다 — 틀어지면 보류로 빠진다.

**차량 영역 제외 + 기준값 0.47 (v0.18)** — Pi 실행에서 차선이 거의 안 잡힌 원인은 두 가지였다. ① 점선 빈칸과 앞차 가림으로 한쪽 윈도 적중이 모자라 피팅 자체가 안 됨, ② 앞차 옆면·뒷면의 세로 모서리가 "가장 안쪽 쌍"으로 뽑힘. 그래서 검출된 차량 박스(신뢰도 ≥ `vehicle_exclusion.min_box_confidence` 0.25, 좌우 `pad_ratio` 5% 확장)를 조감도로 옮겨 차선 후보 마스크에서 지우고, 면적의 `occluded_window_ratio`(50%) 이상이 차량인 윈도는 적중률 분모에서 뺀다(분모 하한 `n_windows`). 검출 주기 사이 프레임은 직전 검출 박스를 그대로 쓴다. 같은 검증 247장(노트북 12·14번 셀):

| 방식 · 기준값 | 원본 가용률 / 오답 | 320px 가용률 / 오답 | 틀어짐 196장 통과 |
|---|---|---|---|
| 이전 (제외 없음) · 0.5 | 15% / 0 | 14% / 0 | 0 |
| 차량 제외 · 0.5 | 16% / 0 | 17% / 0 | 0 |
| 차량 제외 · 0.45 | 19% / 0 | 19% / 0 | 0 |
| 차량 제외 · 0.48 | 18% / 0 | 17% / 0 | 0 |
| 차량 제외 · 0.42 | 21% / **1** | 21% / 0 | 0 |

기준값은 0.45·0.48이 모두 오답 0인 사이의 **0.47**로 정했다 — 차량 제외 시 오답의 신뢰도 최고값 0.428보다 0.04 위. 직전 프레임 마스크를 겹치는 시간 누적(T)도 시험했지만 AI Hub 사진이 1초 간격이라 오히려 떨어졌고(15% → 13%), 실제 연속 영상으로 다시 볼 때까지 보류했다.

> **남은 문제 — 가용률이 여전히 낮다 (17~19%).** 맞게 잡았는데 0.5 미만으로 버려진 프레임 19장을 분해하면 폭 타당성 중앙값 0.85, 적중률 × 피팅 품질 중앙값 0.53 — 점선의 낮은 윈도 적중률이 주로 깎는다. 연속 영상에서 시간 누적 효과를 확인하는 것이 다음 단계다 (5장 미결 사항).

> **알려진 회귀 — 보도블록형 격자 무늬** — S2에서 보도블록 오탐(가중 합산 신뢰도 0.78)을 잡으려고 이전 방식에 RMS 잔차 상한(차로 폭 8%) 하드 게이트를 넣었었다. 현재 방식에서는 격자의 세로 줄눈 하나하나가 깨끗한 세로선이라 top-hat·세로 성분 필터를 통과하고 잔차도 작아, **합성 격자 띠를 차선 쌍으로 잡는다**(신뢰도 0.58). AI Hub 검증 247장에서는 이 유형의 오답이 나오지 않았지만, 인도 옆 도로를 달리는 실차 영상에서 얼마나 나오는지는 모른다. `tests/test_lane_detector.py::test_textured_band_is_not_a_lane`을 strict xfail로 남겨 두었다 — 대응하면 통과로 바뀌며 표시를 지워야 한다.

산출된 잔차 비율은 `LaneModel.fit_residual_ratio`로 함께 반환되어 임계값 튜닝과 디버깅에 쓰인다.

**신뢰도가 중요한 이유**

차선 인식은 이 프로젝트에서 가장 불안정한 구간이다. 차선이 흐린 도로, 앞차에 가려진 차선, 야간·우천 환경에서 성능이 급격히 저하된다. S2 실행 결과 인도 보도블록을 차선으로 오인하는 오탐도 확인되었다(잔차 반영으로 이 사례는 걸러지나, 실차 영상으로 재확인이 필요하다). **신뢰도가 낮을 때 판단을 보류하는 것이 잘못된 offset으로 오탐을 만드는 것보다 낫다.**

스코프 변경(v0.5) 이후 채택 단서가 모두 lane offset에서 파생되므로, 차선 인식은 **판정 전체의 단일 의존 경로**가 되었다. 차선 인식 오류 하나가 여러 단서를 동시에 켤 수 있어(`risk-criteria.md` 4.2), 신뢰도 산출의 정확성이 오탐률을 직접 좌우한다.

**폴백 경로**

`valid == False`인 구간에서는 해당 구간의 **판정을 보류**한다. ~~IMU 기반 지표만으로 판단한다~~ — v0.5에서 IMU 지표가 판정에서 빠졌으므로 IMU 단독 폴백은 폐지되었다. 차선 인식이 최종적으로 불안정하면 폴백이 아니라 차선 인식 방식 자체를 바꾸는 것(딥러닝 전환, 5장 미결 사항)으로 대응한다.

**성능 예산** 25ms

### 3.4 TRACKING — 차량 추적

**책임** 프레임 간 동일 차량에 일관된 ID를 부여한다.

**입력** `VehicleBox[]`
**출력**

```python
@dataclass
class TrackedVehicle:
    track_id: int
    box: VehicleBox
    tracked_frames: int        # 연속 추적 프레임 수
    is_interpolated: bool      # 검출 없이 추적으로 보간된 프레임인지
```

**처리**
- ByteTrack으로 프레임 간 매칭
- 검출이 없는 프레임에서는 이전 궤적으로 위치 보간
- ID switching 발생 시 해당 track의 시계열 데이터를 무효 처리

**구현 방식 (S3)** — ultralytics 내장 `BYTETracker`를 쓰되 `model.track()`은 쓰지 않는다. `model.track()`은 검출과 추적을 한 번에 수행해 DETECTION/TRACKING 경계를 없애고(1.1), 검출 주기 분리도 불가능해지기 때문이다. 대신 `VehicleBox[]`를 tracker가 기대하는 형태로 변환해 넘긴다. ByteTrack은 IoU·칼만 필터 기반이라 추론 비용이 없다.

출력 좌표는 원본 검출 박스가 아니라 **칼만 필터로 평활화된 추적 위치**다. 프레임 간 흔들림이 줄어 lane offset 시계열에 유리하다.

> **⚠️ 검출 주기 분리의 미구현 부분** — `interpolate()`는 현재 직전 위치를 그대로 유지할 뿐 칼만 예측으로 전진시키지 않는다. 검출 주기 분리가 S6 항목이고 현재 `detection.interval`이 dev 기준 1이라 이 경로를 타지 않기 때문이다. S6에서 실제로 쓰려면 5장의 "검출 주기 분리 시 칼만 시간 축" 항목을 먼저 해결해야 한다.

- ID switching 무효 처리는 **미구현** — ID switching 검출 자체가 아직 없다. BDD100K MOT 서브셋으로 빈도를 측정한 뒤(S3) 대응 방식을 정한다.

**관측 충분성 조건**

`tracked_frames`가 config의 최소값(기본 30프레임) 미만인 차량은 거동 분석 대상에서 제외한다. 잠깐 스쳐간 차량의 거동은 신뢰할 수 없다.

**검출 신뢰도와 추적 기준 (v0.16)** — DETECTION은 0.1 이상 박스를 모두 넘기고(`detection.conf_threshold`), TRACKING이 2단계로 쓴다. 0.5 이상(`track_high_thresh`)은 1차 매칭과 새 트랙 생성(`new_track_thresh`)에, 0.1~0.5(`track_low_thresh`~)는 이미 있는 트랙을 잇는 2차 매칭에만 쓴다. v0.15까지는 DETECTION이 0.5 미만을 먼저 버려 2차 매칭이 작동하지 않았다. 근거와 측정 수치는 `risk-criteria.md` 4.1 "객체 검출 신뢰도".

**성능 예산** 10ms

### 3.5 METRICS — 지표 산출

**책임** 차량과 차선의 관계를 수치화하고 시계열로 축적한다.

> **v0.20** — `LaneModel.space`가 `"image"`(ufld 경로)면 조감도 변환 없이 차량 바닥 행에서 좌우 차선 x를 읽어 offset을 낸다(`OffsetCalculator._measure_image`). 기울기 없는 카메라에서 화면의 한 행은 같은 거리의 노면이라 그 행 안의 가로 비율이 보존되므로 같은 offset이 나온다. 차량 바닥이 `LaneModel.measure_y_range` 밖이면 재지 않는다. 연속 횡위치·차로 배정·평활화 등 이후 처리는 두 경로가 같다.

**입력** `TrackedVehicle[]`, `LaneModel`, `IMUData`
**출력**

```python
@dataclass
class VehicleTimeSeries:
    track_id: int
    offsets: deque[OffsetSample]      # 최근 N초
    direction_changes: int
    max_offset_ratio: float
    departure_duration_sec: float

@dataclass
class OffsetSample:
    timestamp: float
    offset_m: float                   # 그 차량이 달리는 차로의 중심 대비 편차, 부호 있음 (v0.15)
    offset_ratio: float               # 차로 폭 대비 비율 (대략 -0.5 ~ +0.5, 히스테리시스만큼 넘을 수 있음)
    lateral_velocity_mps: float       # 연속 횡위치의 시간 미분 (스웨빙·표류용, v0.5 추가)
    lane_confidence: float
    is_interpolated: bool             # 검출 없이 추적만으로 채워진 프레임인지 (v0.7)
    lane_index: int                   # 자차 차로 기준 차로 번호 — 0 자차, -1 좌측, +1 우측 (v0.15)
    position_m: float                 # 차선 경계를 넘어도 끊기지 않는 연속 횡위치 (v0.15)
```

`direction_changes`·`max_offset_ratio`·`departure_duration_sec`은 구현에서 저장 필드가 아니라 `offsets`에서 계산되는 프로퍼티다. 버퍼와 따로 들고 있으면 불일치가 생기기 때문이다. `direction_changes`와 `departure_duration_sec`은 판정 임계값(진폭 하한, 걸침 비율)을 인자로 받으며, 그 값은 RISK가 config에서 읽어 넘긴다 — 지표 산출과 판정 기준을 분리하기 위함이다.

**lane offset 산출 방법**
1. 차량 bounding box 하단 중심점을 차량 위치로 정의
2. 해당 y좌표에서의 자차 차로 중심·폭 계산
3. 자차 차로 중심 대비 거리를 차로 폭으로 나눈 값 `r` 산출 — 옆 차로 차량은 `r ≈ ±1`
4. `round(r)`이 `lane.max_lane_index`(1)를 넘으면 제외 — 두 차로 밖은 차선 외삽을 믿을 수 없다
5. **연속 횡위치** — 직전 값과 정수(차로 1개) 단위로 어긋나면 그만큼 보정해 이어 붙인다(자차가 차로를 바꿔 기준이 한 차로 밀려도 끊기지 않게). 이 값을 평활화하고 횡방향 속도도 여기서 낸다
6. **차로 배정과 차로 내 offset** — 평활화된 연속 횡위치에서 그 차량이 달리는 차로를 빼면 차로 내 offset이다. 차로 배정은 offset이 `0.5 + metrics.lane_switch_hysteresis`를 넘을 때만 바꾼다 — 선을 밟고 달리는 차량의 offset이 매 프레임 +0.5/−0.5로 뒤집혀 사행으로 세지는 것을 막는다
7. 차로 폭 3.5m 기준으로 미터 환산

v0.14까지는 모든 차량을 자차 차로 기준으로만 쟀다. 그래서 옆 차로를 정상 주행하는 차량이 offset ±1로 찍혀 차선 걸침·표류 임계를 항상 넘었고, offset 부호가 바뀌지 않아 사행은 반대로 잡을 수 없었다.

**보정 처리**

| 보정 | 목적 |
|---|---|
| 자차 거동 보상 | IMU yaw/roll로 자차 흔들림 제거. 자차가 흔들리면 앞차가 흔들려 보이는 착시 방지. **v0.5부터 IMU의 유일한 용도** |
| 곡선 도로 보정 | 차선 곡률 기반 기대 궤적을 기준선으로 사용. 정상 곡선 주행의 오판 방지 |
| 시계열 평활화 | 이동평균 또는 칼만 필터로 단일 프레임 이상치 제거 |

**시계열 버퍼**

차량별로 최근 `risk.observation_window_sec`(기본 10초) 구간의 offset 이력을 유지한다. 차량이 화면에서 사라지면 버퍼를 해제한다.

**구현 현황 (S3)** — lane offset 산출, 시계열 버퍼, 평활화(이동평균), 횡방향 속도까지 구현했다. **보정 3종은 아직 들어가지 않았다.**

| 보정 | 상태 |
|---|---|
| 자차 거동 보상 (IMU) | **미구현** — IMU 입력 경로 자체가 없다. 데이터 포맷·전송 주기가 HW 파트와 미협의 상태다 (sprint-plan.md S3 팀 협업) |
| 곡선 도로 보정 | **미구현** — 현재는 차선 중심선을 그대로 기준선으로 쓴다. 곡선 구간에서 오탐 가능성이 있다 |
| 시계열 평활화 | 구현 — 이동평균. 칼만 옵션은 config 키만 있고 미구현(S4) |

횡방향 속도는 인접 프레임 차분이 아니라 평활화 창 길이만큼 뒤의 샘플을 기준으로 기울기를 낸다 — 미분이 잡음을 증폭하기 때문이다 (`risk-criteria.md` 2.6).

**IMU 동기화**

IMU 데이터는 영상 프레임과 다른 주기로 도착한다. 타임스탬프 기준으로 가장 가까운 샘플을 매칭하며, 허용 오차를 초과하면 해당 구간의 자차 거동 보상을 적용할 수 없으므로 offset 샘플을 무효 처리한다.

**성능 예산** 5ms

### 3.6 RISK — 위험 판단

**책임** 시계열 지표로부터 위험 점수를 산출하고 이벤트 생성 여부를 결정한다.

**입력** `VehicleTimeSeries`, `LaneModel.confidence`, `Frame` 품질 정보
**출력**

```python
@dataclass
class RiskAssessment:
    track_id: int
    score: int                        # 0 ~ 100
    level: str                        # low / medium / high
    types: list[str]                  # 감지된 위험 유형
    indicators: dict                  # 지표별 측정값
    should_emit_event: bool
```

**처리 순서**

```
1. 입력 신뢰도 게이팅
   ├ 검출 confidence 미달 → 판단 보류
   ├ 차선 인식 신뢰도 미달 → offset 기반 지표 제외
   ├ 프레임 품질 미달 (블러·밝기 급변) → 판단 보류
   └ 관측 충분성 미달 → 판단 보류
              ↓
2. 지표별 점수 산출
   ├ 차선 걸침 — offset 비율 및 지속 시간
   ├ 사행 — 방향 전환 횟수 및 진폭
   ├ 스웨빙 — 횡방향 속도 급증 후 복귀
   ├ 표류 — 한 방향 저속 횡이동 지속
   └ 속도 불규칙 — bbox 팽창률(1/TTC) 급증, `src/metrics/relative_motion.py` (2026-09-26 채택)
              ↓
3. 결합 판정
   ├ 충족 지표 수 < min_indicators → 이벤트 미생성
   └ 가중 합산으로 통합 점수 산출
              ↓
4. 이벤트 판정
   ├ 히스테리시스 — 시작·종료 임계값 분리
   └ 쿨다운 — 동일 차량 중복 이벤트 억제
```

**구현 현황 (v0.12)** — 입력 신뢰도 게이팅 5개 항목 중 검출 confidence·차선
신뢰도·관측 충분성·자차 속도(LDWS)·**프레임 품질(신규)**은 구현됐다.
프레임 품질(블러·밝기 급변)은 `src/risk/frame_quality.py`의
`FrameQualityChecker`가 담당하며, 카메라 해상도와 무관한 일반적인
컴퓨터 비전 기법(Laplacian 분산, 평균 밝기 변화량)이라 데이터셋·카메라
확정을 기다리지 않고 완성했다. 유효 관측 거리(bbox 면적)는 카메라
마운트 사양 미확정으로 여전히 미구현이다(`src/risk/scorer.py` 모듈
docstring).

**임계값의 출처**

모든 임계값은 `docs/risk-criteria.md`에 근거와 함께 정의되어 있으며, config에서 값을 읽는다. **코드에 임계값을 직접 쓰지 않는다.**

**복수 지표 결합의 근거**

NHTSA 연구에서 단일 단서보다 2개 이상의 단서가 동시 관측될 때 판별 신뢰도가 크게 상승함이 확인되었다. 이를 근거로 `min_indicators`를 2로 설정한다.

**출력 형태 확정** — `RiskAssessment.score`(0~100)를 "음주 의심 점수"로 유지 (2026-09-26 지도교수 확인, `risk-criteria.md` 3.2). 이진 판정 대안은 채택하지 않음 — `score`/`level` 필드와 이벤트 스키마 구조 변경 없음.

**성능 예산** 3ms

### 3.7 EVENT — 이벤트 생성

**책임** 위험 이벤트를 클립과 메타데이터로 구성하고 전송을 관리한다.

**입력** `RiskAssessment`, 프레임 링 버퍼
**출력** 이벤트 JSON + 클립 파일

**처리**
1. 링 버퍼에서 전후 구간 프레임 추출 (전 10초 + 후 5초)
2. PRIVACY 모듈로 비식별화 처리
3. 클립 인코딩 및 저장
4. JSON 메타데이터 생성 — 스키마는 `docs/event-schema.md` 준수
5. 전송 큐 적재

**프레임 링 버퍼**

이벤트 발생 시점 **이전** 영상이 증거로서 더 중요하다. 감지되기까지의 거동이 위험 판단의 근거이기 때문이다. 따라서 항상 최근 N초의 프레임을 메모리에 유지한다.

HW 파트 전체 아키텍처(`docs/system-architecture.md`)에 따르면 이 링 버퍼는 **저장용 main 스트림(1280×720)을 5초 세그먼트 × 12개로 순환 보관(총 60초 용량)**하며, 이벤트 발생 시 전후 15초(전 10초 + 후 5초, `configs/default.yaml`의 `event.clip_pre_sec`/`clip_post_sec`와 일치)를 추출하는 방식이다.

**구현 주체 확정 (v0.5)** — 링 버퍼는 **HW 파트(강섬희)가 구현**하며, 버퍼 크기도 HW 파트가 실측해서 정한다. 따라서 이 저장소의 EVENT 모듈은 링 버퍼를 직접 관리하지 않고, 이벤트 시점과 전후 구간(`clip_pre_sec`/`clip_post_sec`)을 담아 **클립을 요청하고 반환받는** 쪽이다 (HW 시퀀스 다이어그램의 "요청 → 반환" 인터페이스). 위 처리 1단계의 "링 버퍼에서 추출"은 이 요청으로 읽는다.

**클립 요청 인터페이스 구현 (v0.12)** — 요청 인터페이스의 **구체 형태**(함수 호출 / IPC / 파일)는 여전히 HW 파트와 협의되지 않았지만, 이 저장소가 기대하는 **타입 계약**은 `src/event/clip.py`의 `ClipProvider` Protocol로 먼저 정의했다. 지금은 `NullClipProvider`(항상 클립 없음)로 동작해 링 버퍼 미연결 상태를 정직하게 반영하고, HW 쪽 인터페이스가 확정되면 이를 구현하는 클래스 하나만 추가하면 `main.py` 변경 없이 교체된다.

**Store-and-Forward**

통신 단절 시에도 이벤트가 유실되지 않도록 로컬 큐(SQLite)에 우선 저장한다. **로컬 큐 자체는 구현 완료 (v0.12)** — `src/event/queue.py`의 `EventQueue`가 메타/클립 전송 상태를 따로 추적하고, 재전송 시 `event_id` 기준 중복 적재를 막는다. **실제 네트워크 전송(서버 업로드)은 포함하지 않는다** — 그 구현 주체는 여전히 미정이지만(아래 참고), 로컬 저장·상태추적 자체는 외부 팀 결정과 무관하게 데이터셋 없이 완성할 수 있어 먼저 구현했다. HW 파트 아키텍처는 **메타데이터(JSON, 수KB)는 LTE로 즉시 전송하고, 영상 클립(수십MB)은 WiFi 연결 시(정차 후)에 별도로 전송**하는 하이브리드 방식을 전제로 한다 — `docs/event-schema.md` 협의 필요 1번(전송 방식) 참고, 서버 파트 확인 필요.

```
이벤트 발생 → 로컬 저장 (무조건, SQLite 큐)
              ↓
         메타(JSON) → LTE로 즉시 전송
         영상(클립) → WiFi 연결 시(정차 후) 전송
              ↓
         각각 전송 성공 시 로컬에서 개별 삭제, 실패 시 큐 유지 후 재전송
```

재전송으로 인한 중복은 서버가 `event_id`로 판별한다. 이는 앱·서버 파트와 합의된 사항이다.

**성능 예산** 이벤트 발생 시에만 소요. 비동기 처리하여 파이프라인을 차단하지 않는다.

### 3.8 PRIVACY — 비식별화

**책임** 외부로 나가는 영상에서 개인식별 정보를 제거한다.

**처리**
- 번호판 검출 후 가우시안 블러 적용
- 보행자 얼굴 검출 후 블러 적용

**설계 노트**

번호판 검출은 YOLO 모델에 클래스를 추가하는 방식으로 구현한다. 별도 모델을 추가하지 않는다. **번호판 라벨이 있는 파인튜닝 데이터가 필요해 AI Hub 데이터 확보(S5) 이후로 그대로 남는다 — 이 항목은 데이터셋 의존적이다.**

**얼굴 블러 구현 완료 (v0.12)** — `src/privacy/face_blur.py`의 `FaceBlurrer`가 OpenCV 내장 Haar cascade(`haarcascade_frontalface_default.xml`)로 얼굴을 검출해 블러를 적용한다. 아래 "미결 사항"의 검출 방식 선택이 Haar cascade(non-DL)로 해소됐다 — 딥러닝 모델을 추가하지 않고(AGENTS.md 원칙), 데이터셋 없이 지금 완성할 수 있는 방식이기 때문이다. ⚠️ Haar cascade는 YOLO보다 부정확해(정면·충분한 크기 얼굴만 안정적) "완벽한 비식별화"가 아니라 번호판 YOLO 전환 전까지의 1차 방어선으로 본다. 클립 추출 파이프라인(위 EVENT 3.7)이 아직 링 버퍼에 연결되지 않아 실제 호출은 못 하고 있으나, 연결되면 바로 쓸 수 있는 독립 모듈로 먼저 완성해 뒀다.

이벤트 발생 시점에만 수행하므로 상시 성능 부담은 없다. 다만 이벤트가 연속 발생하는 상황에서 병목이 될 수 있어, 비동기 처리 및 큐잉이 필요하다.

**미결 사항** — 비식별화를 Edge에서 수행할지 서버에서 수행할지는 Pi5 성능 여유를 확인한 뒤 확정한다. 현재는 Edge 수행을 기본으로 설계하되, 이벤트 JSON에 `blurred` 플래그를 두어 양쪽 모두 대응 가능하게 한다.
