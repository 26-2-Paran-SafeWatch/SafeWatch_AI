# SafeWatch AI 파트 스프린트 계획

**담당** 설만수 · 소프트웨어학과
**범위** AI 영상 분석 모듈 (차량 검출 · 차선 인식 · 차량 추적 · 위험 판단 · 모델 경량화)
**기간** 16주 / 8스프린트 (2주 단위)
**주당 투입** 16시간

---

## 문서 사용법

- 각 스프린트는 **목표 → 작업 → 산출물 → 완료 조건** 순으로 구성된다.
- 완료 조건(DoD, Definition of Done)을 충족해야 다음 스프린트로 넘어간다.
- 각 스프린트 말미의 **팀 협업 항목**은 다른 파트와 반드시 조율해야 하는 사항이다.
- 체크박스는 진행하며 직접 체크한다.

---

## 전체 로드맵

| 스프린트 | 주차 | 핵심 목표 | Pi5 필요 여부 |
|---|---|---|---|
| S1 | 1~2 | 환경 구축 및 파이프라인 설계 | 불필요 |
| S2 | 3~4 | 차량 검출 + 판단 기준 근거 확보 | 불필요 |
| S3 | 5~6 | 차선 인식 + 추적 + lane offset | 불필요 |
| S4 | 7~8 | 위험 판단 로직 + 기준 정의서 | 불필요 |
| S5 | 9~10 | 데이터 수집 및 파인튜닝 | 수집 시 필요 |
| S6 | 11~12 | 경량화 및 실기기 최적화 | **필수** |
| S7 | 13~14 | 시스템 통합 및 성능 검증 | **필수** |
| S8 | 15~16 | 안정화 및 결과 정리 | **필수** |

**핵심 원칙** — 정확도가 낮더라도 S4 종료 시점까지 "영상 입력 → 이벤트 출력" 전체 흐름을 한 번 관통시킨다. 각 단계를 완벽히 마치고 넘어가는 방식은 병목을 늦게 발견하게 만든다.

# 스프린트 1 — 환경 구축 및 파이프라인 설계

**주차** 1~2주차
**목표** 개발 환경을 갖추고, 이후 모든 작업의 기준이 될 파이프라인 구조를 확정한다.

## 작업 목록

### 개발 환경
- [ ] Python 3.11 가상환경 구성 (venv 또는 conda)
- [ ] PyTorch, Ultralytics, OpenCV, NumPy 설치
- [ ] Git 저장소 생성 및 팀 브랜치 전략 합의
- [ ] GPU 클라우드 서비스 선정 및 계정 생성 (모델 학습용)

### 첫 실행
- [ ] 유튜브 등에서 국내 주행 영상 3~5개 확보 (주간/야간/우천 각각)
- [ ] YOLOv8n 사전학습 모델로 추론 1회 실행 및 결과 육안 확인
- [ ] 프레임당 처리 시간 측정 코드 삽입

### 구조 설계
- [ ] 파이프라인 모듈 경계 정의 (입력 / 검출 / 차선 / 추적 / 판단 / 출력)
- [ ] 각 모듈의 입출력 데이터 형식 문서화
- [ ] 설정값 config 파일 분리 (해상도, 검출 주기, 임계값 등)
- [ ] 처리 시간 로깅 구조 설계 (단계별 ms 기록)

### 데이터 사전 준비
- [ ] AI Hub 회원가입 및 필요 데이터셋 목록 작성
- [ ] 데이터셋 이용 신청 제출 **(승인 대기 시간 있음 — 최우선)**
- [ ] BDD100K 다운로드 경로 확인 — 활용 범위는 아래 참고

**BDD100K 활용 범위** (AI Hub 승인 대기 중 선행 가능, 미국 도로 데이터라 사전학습·검증용으로만 사용하고 판단 기준 검증에는 쓰지 않음)

| 용도 | 내용 | 관련 스프린트 |
|---|---|---|
| 차량 검출 사전학습 | car/truck/bus/rider/motor 등 클래스로 YOLOv8n 선행 파인튜닝 | S1~S2 |
| 추적 성능 검증 | MOT(Multi-Object Tracking) 서브셋으로 ByteTrack ID switching 빈도를 정량 측정 (육안 확인 대체) | S3 |
| 차선 인식 대비책 | lane marking segmentation 라벨 보유 — OpenCV 방식이 실패해 딥러닝 전환 결정 시(`docs/pipeline-architecture.md` 미결 사항) 학습 데이터로 즉시 활용 | S3 종료 시점 |
| 악조건 프록시 테스트 | weather(rainy/snowy)·timeofday(night/dawn-dusk) 속성 라벨 보유 — 실차 20시간 수집(S5) 전에 야간·우천 조건 검출 성능을 미리 점검 | S1~S3 |

## 산출물
- 동작하는 개발 환경
- 파이프라인 구조 설계 문서
- config 파일 초안
- YOLOv8n 추론 데모 (영상 입력 → 검출 결과 시각화)

## 완료 조건
주행 영상을 입력하면 차량 bounding box가 그려진 결과 영상이 출력되고, 프레임당 처리 시간이 콘솔에 기록된다.

## 팀 협업 항목
- **강섬희** — 카메라 모델·해상도·FPS·화각 확정 요청. **장착 위치와 각도도 이 시점에 확정하고 이후 변경하지 않아야 한다.** 캘리브레이션과 수집 데이터 전체가 여기에 의존한다.
- **강섬희** — Pi5 SSH 접속 권한 요청 (중간 확인용)
- **주민규** — 이벤트 JSON 스키마 초안 공유 및 협의 시작

## 리스크
AI Hub 승인이 지연되면 S5 일정이 밀린다. 1주차 내 신청을 완료하고, 승인 전까지는 BDD100K로 선행한다.

# 스프린트 2 — 차량 검출 및 판단 기준 근거 확보

**주차** 3~4주차
**목표** 차량 검출 모듈을 완성하고, 위험 판단 기준의 공신력 있는 근거를 확보한다.

## 작업 목록

### 차량 검출
- [ ] YOLOv8n 추론 래퍼 클래스 구현
- [ ] confidence 임계값, NMS IoU 임계값 튜닝
- [ ] 관심 영역(ROI) 설정 — 하늘·갓길 제외, 전방 차선 영역만 처리
- [ ] 전방 차량 필터링 로직 (화면 중앙 하단 영역 우선)
- [ ] 해상도별 처리 시간 비교 (640 / 416 / 320)

### 판단 기준 근거 조사
- [ ] 한국교통안전공단 11대 위험운전행동 판별 기준 조사 및 정리
- [ ] 운행기록분석시스템(ETAS) 공개 자료에서 임계값 확인
- [ ] NHTSA 음주운전 시각적 판별 지표(24개 단서) 정리
- [ ] 차로이탈경고장치(LDWS) 동작 기준 조사
- [ ] 각 기준을 영상·IMU에서 측정 가능한 지표로 변환 가능한지 검토

### 학습
- [ ] OpenCV perspective transform 학습 및 실습
- [ ] 카메라 캘리브레이션 개념 학습 (픽셀 → 실거리 변환)

## 산출물
- 차량 검출 모듈 (`detector.py`)
- **판단 기준 근거 조사 자료** (심사 대응 및 정의서 기초 자료)
- 해상도별 성능 비교표

## 완료 조건
주행 영상에서 전방 차량이 안정적으로 검출되고, 해상도별 처리 시간이 표로 정리되어 있다. 위험 판단에 사용할 지표 후보가 근거 출처와 함께 목록화되어 있다.

## 팀 협업 항목
- **강섬희** — Pi5 온도·fps 로깅 결과 공유 요청. 액티브 쿨러 장착 전후 비교 데이터 확보
- **주민규** — 이벤트 JSON 스키마 확정. 확정 이후에는 상호 합의 없이 변경하지 않는다

## 참고
검출 자체는 난이도가 높지 않다. 이 스프린트의 실질적 무게는 **판단 기준 근거 조사**에 있다. 심사의견 2번에 대한 직접적인 답이므로 소홀히 하지 않는다.

# 스프린트 3 — 차선 인식 및 차량 추적

**주차** 5~6주차
**목표** 차선을 검출하고 차량을 추적하여, lane offset 시계열 데이터를 생성한다.

## 작업 목록

### 차선 인식 (본 프로젝트 최대 난관)
- [ ] 관심 영역 설정 및 perspective transform (bird's eye view 변환)
- [ ] 색상·엣지 기반 차선 후보 추출 (HLS 색공간 + Canny)
- [ ] sliding window로 차선 픽셀 탐색
- [ ] 2차 다항식 피팅으로 차선 곡선 산출
- [ ] 차선 인식 신뢰도 지표 산출 (피팅 잔차, 좌우 차선 평행도)
- [ ] 차선 미검출 구간 처리 (직전 프레임 값 유지 또는 판단 보류)

### 차량 추적
- [ ] ByteTrack 연동 (Ultralytics 내장 기능 활용)
- [ ] track_id 유지 확인 및 ID switching 발생 빈도 측정 — BDD100K MOT 서브셋으로 정량 측정 (S1 표 참고)
- [ ] 최소 추적 지속 프레임 조건 적용

### lane offset 계산
- [ ] 차량 bounding box 하단 중심점을 차량 위치로 정의
- [ ] 해당 y좌표에서의 차선 중심 좌표 산출
- [ ] 픽셀 거리 → 실거리(m) 변환 (차로 폭 3.5m 기준 캘리브레이션)
- [ ] 차량별 offset 시계열 버퍼 구현 (최근 10초 유지)

### 데이터 확보
- [ ] AI Hub 데이터셋 다운로드 및 구조 파악
- [ ] BDD100K 라벨 포맷 확인 — lane marking segmentation 라벨은 차선 인식 딥러닝 전환 시(이번 스프린트 종료 시점 결정) 대비용으로 별도 보관 (S1 표 참고)
- [ ] 라벨링 도구(CVAT) 설치 및 사용법 숙지

## 산출물
- 차선 인식 모듈 (`lane_detector.py`)
- 차량 추적 및 offset 계산 모듈 (`tracker.py`, `offset.py`)
- 공개 데이터셋 확보 및 전처리 환경

## 완료 조건
주행 영상에서 차선이 검출되고, 전방 차량의 lane offset 값이 프레임마다 수치로 출력된다. 차량이 화면에서 사라지기 전까지 동일한 track_id가 유지된다.

## 팀 협업 항목
- **강섬희** — IMU 데이터 포맷 및 전송 주기 협의. 영상 프레임과의 시간 동기화 방식 결정 (타임스탬프 기준)

## 리스크
차선 인식은 이 프로젝트에서 가장 과소평가되기 쉬운 부분이다. 차선이 흐린 도로, 차선을 가린 앞차, 야간·우천 환경에서 성능이 급격히 저하된다.

**대응 계획** — 차선 인식 실패 시에도 시스템이 동작하도록, 차선 없이 IMU와 차량 상대 거동만으로 판단하는 폴백 경로를 함께 설계한다. 6주차 종료 시점까지 차선 인식이 불안정하면 딥러닝 기반 모델(UFLD 등) 도입을 재검토한다.

# 스프린트 4 — 위험 판단 로직 및 기준 정의서

**주차** 7~8주차
**목표** 위험 점수 산출 로직을 완성하고, 판단 기준을 문서로 확정한다. 전체 파이프라인을 처음으로 관통시킨다.

## 작업 목록

### 판단 기준 정의서 작성
- [ ] S2에서 조사한 공공기관 기준을 측정 지표로 변환
- [ ] 지표별 임계값 설정 및 근거 명시
- [ ] 위험 유형 분류 체계 확정 (차선 이탈 / 사행 / 급가감속 / 급진로변경)
- [ ] **판단 기준 정의서 문서화** (제출물)

### 위험 점수 산출
- [ ] 지표별 점수 산출 함수 구현
- [ ] 가중 합산을 통한 0~100점 통합 점수 산출
- [ ] 위험 등급(low / medium / high) 매핑

### 오탐 억제 로직
- [ ] **입력 신뢰도 게이팅** — 검출 confidence, 차선 인식 신뢰도, 프레임 품질(블러·밝기) 검사. 미달 시 판단 보류
- [ ] **자차 거동 보상** — IMU yaw/roll로 자차 흔들림 보정 후 상대 거동 산출
- [ ] **곡선 도로 보정** — 차선 곡률 기반 기대 궤적을 기준선으로 사용
- [ ] **복수 지표 결합 판정** — 2개 이상 지표 동시 충족 시에만 이벤트 생성
- [ ] **히스테리시스** — 이벤트 시작·종료 임계값 분리
- [ ] **쿨다운** — 동일 차량 대상 일정 시간 내 중복 이벤트 억제

### 이벤트 출력
- [ ] 이벤트 발생 시 전후 구간 클립 추출 (전 10초 + 후 5초)
- [ ] 확정된 JSON 스키마로 이벤트 데이터 생성
- [ ] 로컬 이벤트 큐 구현 (전송 실패 대비 Store-and-Forward)

## 산출물
- 위험 판단 모듈 (`risk_scorer.py`)
- **위험운전 판단 기준 정의서** (지표 · 임계값 · 근거 명시)
- End-to-End 동작 데모 (영상 입력 → 이벤트 JSON + 클립 출력)

## 완료 조건
**주행 영상을 입력하면 위험 구간에서 이벤트 JSON과 클립 파일이 생성된다.** 정확도는 낮아도 무방하다. 전체 흐름이 끊김 없이 이어지는 것이 이 스프린트의 핵심이다.

## 팀 협업 항목
- **주민규** — 생성된 더미 이벤트를 전달하여 앱·서버 측 개발을 선행할 수 있도록 지원
- **팀 전체** — S5 실차 데이터 수집 일정 및 담당 분배 논의 시작

# 스프린트 5 — 데이터 수집 및 파인튜닝

**주차** 9~10주차
**목표** 국내 도로 데이터를 확보하고 모델을 국내 환경에 맞게 미세조정한다.

## 작업 목록

### 실차 데이터 수집
- [ ] 수집 경로 사전 설계 (수도권 일반도로 + 고속도로)
- [ ] 수집 조건 분산 계획 — 주간/야간, 맑음/우천, 도심/교외
- [ ] 팀원별 주행 담당 분배 및 일정 확정
- [ ] **목표 20시간 이상 확보**

## 부록 C — 상시 유의사항

**측정을 습관화한다**
단계별 처리 시간, fps, 정확도를 매 실험마다 기록한다. 나중에 몰아서 측정하려면 재현이 어렵고, 이 기록이 그대로 KPI 검증 근거가 된다.

**설정값을 하드코딩하지 않는다**
해상도, 검출 주기, 임계값은 config 파일로 분리한다. Pi5에서 튜닝할 때 코드 수정 없이 값만 조정할 수 있어야 한다.

**PC와 Pi5의 성능 차이를 항상 염두에 둔다**
PC에서 여유 있게 동작하던 코드가 Pi5에서는 4~5배 느려진다. 개발 단계부터 처리 시간 예산을 의식하며 작성한다.

**문서를 미루지 않는다**
판단 기준 정의서는 제출물이자 심사 대응 근거다. 구현과 동시에 작성하는 편이 훨씬 수월하다.

**인터페이스 확정 후에는 변경하지 않는다**
카메라 장착 위치, 이벤트 JSON 스키마는 한 번 정하면 상호 합의 없이 바꾸지 않는다. 변경 시 이미 수집한 데이터나 상대 파트의 작업이 무효화된다.
