**AI Hub 다운로드 시점** — 신청(승인 요청)은 지금 하되, **실제 파일 다운로드는 S5(9~10주차) 파인튜닝 착수 시점까지 미룬다.** 전체 코퍼스는 수백GB~175TB 규모라 로컬에 받을 이유가 없다. (1) GPU 클라우드가 정해지면 그 인스턴스에 직접 받고, (2) 처음엔 시나리오/날짜별로 선택 가능한 서브셋(수천~수만 장)만 받아 파이프라인 검증 후 필요하면 확장한다.

**다운로드·파인튜닝 환경 확정 (2026-09-28)** — 팀원 데스크탑(RTX 4070, 2TB 저장공간)을 쓰기로 결정. 국내 IP라 AI Hub 다운로드 제한도 안 걸리고, 저장공간·GPU 파인튜닝을 한 곳에서 해결. 맥에서 겪은 이슈 중 이어질 수 있는 것:
- 저장공간 부족 문제는 해소되지만, `aihubshell`의 두 가지 버그(위 "⚠️ aihubshell 자체 버그 2개" 참고 — 다운로드 실패 미감지, 멀티파트 병합 순서)는 **OS와 무관한 스크립트 로직 버그**라 그대로 재현될 수 있음. 특히 병합 순서 버그는 조각(part) 개수가 많은 대용량 파일일수록 걸릴 확률이 높음
- 윈도우에서는 AI Hub 안내상 `aihubshell` 실행에 WSL이 필요함

**다운로드 방법** (승인 완료 후에만 가능) — 웹 브라우저로 파일 목록에서 zip을 개별 클릭해 받을 수도 있지만, 데이터셋이 원본/부위(bb·fs·pg·sl 등)/도로 유형별로 잘게 쪼개진 수십~수백 개 zip으로 구성돼 있어(예: 도로주행영상 = 8개 조합 × Training/Validation) 서브셋만 고를 거면 **`aihubshell`(공식 CLI) 사용을 권장**:
1. AI Hub 로그인 후 API Key 발급(마이페이지)
2. `curl -o aihubshell https://api.aihub.or.kr/api/aihubshell.do && chmod +x aihubshell`
3. `aihubshell -mode l -datasetkey <dataSetSn>` 으로 파일별 filekey 조회
4. `aihubshell -aihubapikey <키> -mode d -datasetkey <dataSetSn> -filekey <filekey1,filekey2,...>` 로 필요한 zip만 선택 다운로드 (filekey 생략 시 전체 다운로드)
분할 압축(.zip.part*)으로 내려오므로 리눅스(또는 WSL)에서 `cat`으로 병합 후 압축 해제 필요.

**⚠️ `aihubshell` 자체 버그 2개 (2026-09-27, 도로주행영상 Validation 원천데이터 14GB로 다운로드 시도 중 발견)** — 로컬 환경 문제가 아니라 스크립트 결함이라 어디서 받든(외장하드·학교서버·클라우드) 똑같이 겪는다. 큰 파일(멀티파트) 받기 전에 아래 두 가지를 먼저 고치고 시작할 것:
1. **다운로드 실패 감지 안 됨** — `down_func()`에서 `curl_exit_code=$?`가 curl이 아니라 직전 `echo "Request successful..."` 명령의 종료코드를 읽어와서 항상 0(성공)으로 나온다. 즉 **네트워크가 끊겨 다운로드가 중간에 잘려도 스크립트는 계속 "성공"으로 진행**해 깨진 파일을 그대로 병합·완료 처리한다. → 자체 구현으로 우회할 경우 `curl`을 별도로 실행해 `$?` 또는 `${PIPESTATUS[0]}`를 직접 확인해야 한다.
2. **여러 조각(part) 파일 병합 순서가 뒤섞일 수 있음** — `merge_parts()`의 `find ... | sort -t'.' -k2V`가 파일명 `이름.zip.partNNNN`을 `.`으로 나눴을 때 2번째 필드(`zip`, 모든 조각이 동일)로 정렬한다. 조각을 구분 짓는 실제 숫자(파트 오프셋)는 3번째 필드라 **정렬이 사실상 안 먹혀서, 조각이 여러 개(멀티GB 파일)일 때 순서가 뒤바뀌어 병합될 수 있다.** 실제로 14개 조각짜리 14GB 파일에서 매번 정확히 같은 크기로 깨진 zip이 나온 것과 일치. → 자체 병합 시 파일명 끝 `.part` 뒤 숫자만 뽑아 **숫자로** 정렬해야 한다.
3. (참고, 버그는 아님) **디스크 공간이 2배 이상 필요** — `curl -o download.tar`로 통째로 받은 뒤 `tar -xvf`로 푸는 구조라, 압축 해제 중 원본 tar와 풀리는 파일이 동시에 존재해 순간적으로 **파일 크기의 2배 이상**의 여유 공간이 필요하다. 43GB 여유에서도 14GB 파일 하나를 못 받고 반복 실패했다 — 로컬에서 시도하기 전에 파일 크기의 3배 이상 여유공간을 확보할 것.

> 개인별 계획서(2026-2학기 파란학기제 신청서) "4. 개인별 추진일정"의 3~4주차 항목이 "차량 검출 및 차선 인식 모듈 구현"으로 명시되어 있어, 차선 인식 착수 시점을 이번 스프린트로 당겼다 (기존안은 5~6주차).

## 작업 목록

### 차량 검출
- [x] YOLOv8n 추론 래퍼 클래스 구현 — `src/detection/detector.py`
- [ ] confidence 임계값, NMS IoU 임계값 튜닝 — config로 분리는 완료(`detection.conf_threshold`/`iou_threshold`), 실차 영상으로 실측 튜닝은 미착수 (데이터 확보 후)
- [x] 관심 영역(ROI) 설정 — 하늘·갓길 제외, 전방 차선 영역만 처리 — 구현 완료(`detection.roi_top_ratio`). ⚠️ 대시캠 샘플 영상이 아직 없어 실제 도로 영상으로는 미검증 (ultralytics 번들 이미지로만 코드 경로 검증)
- [x] 전방 차량 필터링 로직 (화면 중앙 하단 영역 우선) — `detection.center_region_ratio` 기반 중앙 대역 필터, `tests/test_detector.py`로 검증

## 부록 C — 상시 유의사항

**측정을 습관화한다**
단계별 처리 시간, fps, 정확도를 매 실험마다 기록한다. 나중에 몰아서 측정하려면 재현이 어렵고, 이 기록이 그대로 KPI 검증 근거가 된다.

**설정값을 하드코딩하지 않는다**
해상도, 검출 주기, 임계값은 config 파일로 분리한다. Pi5에서 튜닝할 때 코드 수정 없이 값만 조정할 수 있어야 한다.

**PC와 Pi5의 성능 차이를 항상 염두에 둔다**
PC에서 여유 있게 동작하던 코드가 Pi5에서는 4~5배 느려진다. 개발 단계부터 처리 시간 예산을 의식하며 작성한다.

**문서를 미루지 않는다**
판단 기준 정의서는 제출물이자 심사 대응 근거다. 구현과 동시에 작성하는 편이 훨씬 수월하다.

**인터페이스 확정 후에는 변경하지 않는다**
카메라 장착 위치, 이벤트 JSON 스키마는 한 번 정하면 상호 합의 없이 바꾸지 않는다. 변경 시 이미 수집한 데이터나 상대 파트의 작업이 무효화된다.
